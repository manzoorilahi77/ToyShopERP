> Base URL, auth headers, the success/error envelope, error codes, pagination and
> `?format=` export are defined once in
> [api-conventions.md](../../../foundation/api-conventions.md) — this doc references, does
> not repeat them.

## 1. Overview

The Stock module answers one question everywhere in the ERP: **how many of this product
are physically on hand right now, and why?** It never stores a mutable counter. Every
number it returns is **derived from the immutable `stock_movements` event log**
(`on_hand = SUM(quantity_delta)`), so concurrent offline sales are *additive* and can
never cause a lost update. See
[sync-and-conflict-resolution.md](../../../foundation/sync-and-conflict-resolution.md).

Callers:

| Caller | Uses |
|---|---|
| Staff app | reads on-hand hints for the sell grid (UX only; not authoritative) |
| Owner app | Low-Stock / Aging-Stock alert tiles with one-tap drill-down |
| Owner Web | [web/stock-report](../../web/stock/stock-report.md) — current stock, aging, low, audit ledger |
| Sync worker | posts manual adjustments; triggers reconcile after apply |

Business risks addressed (R4 Stock Reports, R1 stock reconciliation):
- **Aging stock piling up unnoticed** → `GET /stock/aging` with a "push for clearance" action.
- **Silent stock-outs** → `GET /stock/low` with a "create purchase order" shortcut.
- **Untraceable stock loss** → `GET /stock/movements` full audit ledger (who/when/device).
- **Counter drift after offline sync** → `POST /stock/reconcile/{productId}` recomputes truth.

## 2. Data model touched

Tables (canonical names & columns from
[data-model.md](../../../foundation/data-model.md)):

| Table / view | Role | Read / Write |
|---|---|---|
| `stock_movements` | **source of truth** — append-only event log | read + insert (adjustments) |
| `v_current_stock` | derived view `product_id → on_hand = SUM(quantity_delta)` | read |
| `products` | catalog metadata: `reorder_threshold`, `aging_threshold_days`, `is_active`, `name`, `image_url`, `category_id`, `shelf_location` | read |
| `app_settings` | `aging_threshold_days`, low-stock defaults | read |
| `categories` | filter/group by category | read |
| `sync_log` | idempotency ledger for adjustments | write |
| `notifications` | oversold / low-stock / aging alerts (generated by worker, see [reports-notifications](../reports-notifications/reports-notifications-api.md)) | write (side-effect) |

> **Never** `UPDATE products SET qty = …`. Stock changes only ever `INSERT` a
> `stock_movements` row. `v_current_stock` (or its materialized cache) is recomputed, not
> mutated in place.

### `POST /stock/adjustments`

- **Purpose** — record a **manual stock correction** (physical count, damage, theft, found stock) as a `stock_movements(movement_type='adjustment', ref_type='manual')` row with a `quantity_delta` and a `note`.
- **Auth** — owner (accountant 🧩). Not staff.
- **Idempotency** — **Yes.** Send `Idempotency-Key: <client_uuid>` header (= body `client_uuid`). Replays return the original movement with `DUPLICATE_IGNORED`. See [api-conventions §6](../../../foundation/api-conventions.md).
- **Path / query params** — none.
- **Request body**

| Field | Type | Required | Validation | Notes |
|---|---|---|---|---|
| `client_uuid` | uuid | yes | UNIQUE | idempotency key; also sent as header |
| `product_id` | int | yes | product exists & active | |
| `quantity_delta` | int | yes | ≠ 0 | **signed**: `+5` found stock, `-2` damaged |
| `note` | string | yes | ≤ 255 | reason (audit); required for manual adjustments |
| `occurred_at` | datetime | no | ISO-8601 | business time; defaults to server now |

- **Response `201`**

| Field | Type | Notes |
|---|---|---|
| `movement_id` | int | new `stock_movements.id` |
| `product_id` | int | |
| `quantity_delta` | int | echoed |
| `on_hand` | int | recomputed on-hand **after** applying the adjustment |
| `note` | string | |
| `occurred_at` | datetime | |

```json
// Request
{ "client_uuid": "7c1e-uuid", "product_id": 22, "quantity_delta": -2,
  "note": "2 units water-damaged in backyard", "occurred_at": "2026-07-02T09:00:00+05:30" }
// Response 201
{ "ok": true, "data": {
  "movement_id": 90233, "product_id": 22, "quantity_delta": -2,
  "on_hand": 5, "note": "2 units water-damaged in backyard",
  "occurred_at": "2026-07-02T09:00:00+05:30" },
  "meta": { "request_id": "req_c33" } }
```

- **Status codes & errors**

| HTTP | `error.code` | When |
|---|---|---|
| 201 | — | created |
| 400 | `VALIDATION_ERROR` | `quantity_delta = 0`, missing `note`/`product_id` |
| 403 | `FORBIDDEN` | role not owner/accountant |
| 404 | `NOT_FOUND` | product does not exist |
| 409 | `DUPLICATE_IGNORED` | `client_uuid` already applied (success to client) |
| 422 | `BUSINESS_RULE` | adjustment would drive on-hand < 0 **and** `allow_negative=false` policy (records + flags instead — see §5) |

## 5. Business logic & validation

**Event-sourced computation (the core idea).**
On-hand is *always*:
```sql
SELECT COALESCE(SUM(quantity_delta), 0) FROM stock_movements WHERE product_id = ?;
```
- `purchase_in` and `return_in` are **positive** deltas; `sale_out` is **negative**;
  `adjustment` is **signed**; `void_reversal` reverses a prior movement (e.g. a voided sale
  appends `+qty`). We never edit or delete a movement — corrections are new rows. This is
  why two staff selling the same toy offline both count (§6).
- `v_current_stock` is a convenience view; at scale it is backed by a **materialized cache
  table** refreshed on every apply and by `POST /stock/reconcile/{productId}`.

**Aging computation.** For each product with `on_hand ≥ 1`:
```
age_days = today − COALESCE(last(sale_out).occurred_at, first(purchase_in).occurred_at)
threshold = COALESCE(products.aging_threshold_days, app_settings.aging_threshold_days)
include if age_days ≥ threshold
```
`tied_value = on_hand × products.cost_price`.

**Low-stock computation.** `is_low = on_hand ≤ COALESCE(query.threshold, products.reorder_threshold)`;
`deficit = max(threshold − on_hand, 0)` is the suggested reorder quantity.

**Adjustment write (transactional).**
```
BEGIN
  IF exists(client_uuid) → return DUPLICATE_IGNORED + original movement
  validate product active, quantity_delta ≠ 0, note present
  INSERT stock_movements(movement_type='adjustment', ref_type='manual',
                         ref_client_uuid=client_uuid, quantity_delta, note, staff_id, device_id)
  INSERT sync_log(transaction_type='stock_adjustment', status='applied', client_uuid)
  on_hand = recompute(product_id); refresh cache
  IF on_hand < 0 → emit notification(type='low_stock'/oversold), flag product for count
  INSERT audit_log(action='stock.adjustment', before/after)
COMMIT
```

**Negative-stock policy.** Consistent with the sync doc: the server **never refuses a
recorded reality**. A completed sale that drives on-hand below zero is still recorded; the
product is flagged and an oversold/low-stock notification is raised for a physical count.
A *manual* negative adjustment that would go below zero is allowed only when policy permits
(default: allow + flag; strict mode returns `422 BUSINESS_RULE`).

## 6. Sync & conflict handling

- **Adjustments are sync-replayable** exactly like sales/purchases: `client_uuid` +
  `Idempotency-Key`; the outbox can push them offline. Duplicate push → `DUPLICATE_IGNORED`.
- **No lost updates on stock.** Because on-hand = `SUM(quantity_delta)`, concurrent offline
  `sale_out` rows from different devices **both append and both count** — order-independent.
  Example from the sync doc: on-hand 10, Staff A sells 3, Staff B sells 4 offline → after
  sync, on-hand 3 regardless of arrival order.
- **Reconcile is the recovery tool.** After any suspected drift (bulk import, crashed apply,
  oversold), `POST /stock/reconcile/{productId}` re-derives truth from the log.
- Full rules: [sync-and-conflict-resolution.md](../../../foundation/sync-and-conflict-resolution.md).

## 7. Edge cases & failure modes

1. **Oversold (on-hand < 0).** Real sales that outpace recorded purchases. We record the
   sale, floor UX display at 0, raise an oversold notification, and flag for count. `GET
   /stock/{id}` still reports the true (negative) `on_hand` for audit.
2. **Duplicate adjustment push.** Same `client_uuid` twice → `409 DUPLICATE_IGNORED`, one row.
3. **Sale references a product not yet synced.** Handled upstream by FIFO outbox ordering;
   the product create is pushed first. Stock endpoints only ever read committed products.
4. **Reconcile during heavy write.** Recompute reads the full log at a snapshot; a movement
   inserted mid-recompute is picked up by the next reconcile/apply — never double-counted.
5. **Aging with never-sold products.** `last_sold_at = null`; age counts from first
   `purchase_in`. Products with `on_hand = 0` are excluded (nothing sitting).
6. **Adjustment on inactive product.** `422 BUSINESS_RULE` — reactivate first (or use a
   `return_in` via the purchases flow).

## 8. Performance & indexing

| Query | Index relied on |
|---|---|
| on-hand per product | `stock_movements.idx_product (product_id)` + materialized `v_current_stock` cache |
| ledger by product/date | `idx_product`, `idx_occurred (occurred_at)` |
| ledger by ref | `idx_ref (ref_type, ref_id)` |
| catalog filters | `products.idx_cat`, `idx_supplier`, `idx_shelf`, `idx_color`, `ft_name` |

- **Volume:** movements grow fastest (every sale line = one row). Keep the aggregate in a
  **materialized cache** refreshed on apply; recompute-from-log only on reconcile.
- **Pagination:** `/stock/movements` uses **cursor** pagination (large ledger); the summary
  tiles (`/stock`, `/stock/low`, `/stock/aging`) use page-based on the much smaller
  product set.
- **Export:** `?format=csv|xlsx` streams for the web stock report.
